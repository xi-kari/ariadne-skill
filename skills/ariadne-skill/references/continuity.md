# Delivery, collaboration and continuity

## Keep a live result

The unit of continuation is the user's question and current work, not a module invocation. Keep the objective, relevant constraints, current result, decisive grounds, unresolved issues and next dependent step recoverable. Use a short note when the conversation is enough; save a task file when work spans people, sessions, artifacts or substantial revisions. Do not require a universal form before thinking (§2.14, §11.13, §13.11.2).

A useful working note might contain:

```text
Question and requested endpoint
Current answer or artifact, with its location
Grounds and assumptions that matter
Open issues and the claims they affect
What changed since the previous result
Next useful step and any genuine blocker
```

This is a prompt for continuity, not a required schema. Reuse source files, version control, research notes and tool receipts instead of creating duplicate ledgers.

## Continue from the changed dependency

| New input | Continue by |
|---|---|
| Additional evidence | Verify its source, timing and support, then update only dependent claims. |
| A challenged target, boundary or given constraint | Record the reasoned reopening and the old/new relationship; preserve prior results. |
| A new preference or decision rule | Recompare affected options while retaining factual findings. |
| A changed task constraint | Recheck feasibility and revise the actual artifact; do not silently keep a now-invalid design. |
| A forecast outcome | Append an assessment to the frozen registration; never overwrite the original target or inputs. |
| An execution receipt | Determine which step it proves and inspect the external state or consequence still required. |
| An objection | Answer the actual reason, revise where warranted, or explain why the existing result still stands. |

Distinguish an evidence update from a mechanism advancing through time. New knowledge about a past event does not mean the event happened again. The date an event occurred, the date it was observed and the date it entered a model can differ (§11.3.2).

## Work with other agents

Delegate a bounded question with the relevant actual materials, task, assumptions, scope, expected result and file ownership. Supply no preferred conclusion. A task may need independent review, but agreement between models does not establish independent empirical support. A summary helps orientation; it does not replace the underlying material when a judgment depends on details (§2.7, §13.11.1).

Run independent work in parallel. Order work that shares a mutable object, finite resource, prerequisite or option set. Record which artifact and version a worker actually consumed. Resolve incompatible boundaries, evidence interpretations and value premises explicitly; preserve disagreements that remain.

When a collaborator or tool is unavailable, say what could not be done. Continue the parts the current host can perform faithfully. There is no package-level requirement to stop because a former peer skill is absent: the installed package contains the methods, and delegation is a host capability rather than an epistemic gate.

## Use tools to reach the requested endpoint

Keep suggestion, tool request, application execution, external state and downstream consequence separate. Choose the relevant check from the user's actual task (§13.11.1–13.11.2):

- A draft: save it, reopen it and check the requested contents and format.
- Code: inspect and modify the actual project, then run tests that probe the changed behavior and relevant failure cases.
- A schedule: verify coverage, conflicts, capacity and timing, then deliver the actual usable schedule.
- An external record: inspect the resulting record and scope of change.
- A remedy: check that the resource, service or corrected right actually reaches its intended position.

Use the user's existing authorization and the host's rules. Method completion does not create a new approval requirement. When a real missing permission blocks a consequential step, finish the safe reviewable product and identify the specific dependent action. Do not report supplied authority as unknown merely because a template was not filled.

A timeout leaves the outcome uncertain. Inspect the request ID or target state before retrying an action that could duplicate a mutation. A stop request, receipt of the stop, termination of work already in flight and remedy for effects already produced are different endpoints.

## Preserve history without freezing current work

Maintain a complete current answer or artifact, integrating mature revisions rather than accumulating disconnected patches. Preserve the earlier failure, evidence cutoff and disposition through version control, appended records or a concise change account. A new question cannot turn the old test into a success. A correct earlier result stays correct within its original conditions even when a broader claim fails (§2.9, §6.3, §16.19).

If the user edited an artifact, read its actual current version before making changes. Do not replace their changes with remembered text. Track text identity, theory identity, artifact schema, software version and the version actually used by a run separately; a matching hash does not demonstrate successful migration of behavior.

## Stop for a reason that belongs to the task

Finish when the requested endpoint is achieved and the required checks are complete. Pause a dependent claim when its necessary input is genuinely unavailable. Explain a proportional work budget when further investigation would cost more than it can reasonably add, including delay, privacy and maintenance burden.

Do not stop because a fixed number of modules ran, two headlines were unchanged, or a substantive branch seems unlikely to reverse the preferred answer. A branch may explain a failure, limit scope, reveal an affected position or improve the artifact. A theory-specific stopping rule applies only to the procedure for which it was defined (§16.7).

Do not promise autonomous monitoring without an actual arrangement. A dated next review can be a recommendation or an agreed task; it is not evidence that a background job exists. Leave the next live question clear enough to resume without claiming the future work has already happened.
