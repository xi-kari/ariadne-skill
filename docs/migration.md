# 迁移到单入口与可组合路径

当前开发架构使用一个 `ariadne-skill` 安装包。旧 `v2.0.0` 标签中的十个入口与旧来源版本仍属于那个发布快照；本次架构改动不创建新标签，也不改变历史版本的内容。README 标注开发分支和稳定版的实际状态。

## 使用与安装

新任务只调用 `ariadne-skill`。入口根据所需成果读取内部路径和专门资料。它不要求用户学习新的模块名，也不要求每次使用全部路径。

在准备迁移的宿主中，用其正常的卸载或更新方式移除旧的九个独立 Ariadne 入口，再安装相应的新版本，避免宿主继续发现过时提示词。先检查安装位置和本地修改，不批量删除不明目录。本仓库的开发和评测不改动全局 skills 目录。

| 旧职责或入口 | 当前去向 |
|---|---|
| framing、evidence | `understand`、共同 kernel/responsibility，以及 object/evidence/domain 理论资料 |
| scale、mechanism | 由 `understand`、`discover`、`project`、`create` 按问题组合；专门转换、表征、闭合与机制条件留在深库 |
| human | 横跨具体路径的受影响位置、负担与行动条件；人类变量卡、状态原型与圈层资料按需读取 |
| dynamics、forecast | `project`；正式前瞻另用目的专一的合同和登记工具 |
| choice | `decide`；规范理由、实质保护与实施条件保持区分 |
| audit | 共享的检验操作，以及完整的 `review` 路径 |
| 原主入口的全流程路由 | 新入口依据任务结果编排，可重开、分叉、直接构建和持续修订 |

这张表用于寻找旧内容，不规定新架构的一对一对应。路径数量也不是新的固定配额。

## 已有记录

Method Record **2.0 与 2.1** 仍可验证。显式要求旧格式时，读取安装包内 `references/legacy/method-record.md`，使用 `scripts/validate_record.py`。旧模块名作为历史枚举继续存在，不能据此推断对应独立技能仍然安装。原有 `schemas/method-record.schema.json` 与安装包中的 schema 保持一致。

不把旧记录重新包装成已经发生的新运行，也不改写旧来源身份或历史失败。2.0 记录保留其原约束；2.1 才支持其新增字段与候选数量例外。对旧记录的验证只承诺其自身的交换合同，不支配普通回答、草案或当前任务的知识地位。

安装包内的验证器是唯一旧语义实现，仓库包装器调用同一份代码。新路径无须先形成旧记录再继续工作。

## 正式前瞻

新的 `contracts/forecast.schema.json` 使用专用 **artifact_version 1.0**，与理论版本 v2、旧 Method Record 2.1 和软件版本无关。`scripts/forecast.py` 提供登记、追加观察和校验，见[完整合同与例子](../skills/ariadne-skill/contracts/forecast.md)。

旧预测记录可以作为历史材料，不能在结果已知后重新登记为一次新的事前预测。新登记应使用新的唯一 ID，保留关联原件、原始条件和失败；观察与修订追加而不覆盖。

本地工具需要 Python 3.10+、jsonschema 与 POSIX 安全文件操作。Linux 环境已有测试；macOS/WSL 具备相应系统接口但不等于已完成这些平台的实际运行验证，原生 Windows 当前不支持此登记工具。技能的文本路径不因此受限。可使用符合相同冻结和评价责任的外部登记程序，并准确说明实际使用的程序。

## 链接、集成与扩展

过去指向已删除独立入口的链接，应改到当前路径或相应的 `references/library/` 文件；需要呈现历史时，固定到原标签或提交。单文件版包含 manifest 选择的入口、共享指导、路径及前瞻说明，深库、schema 和工具通过链接提供，不假装已执行。

集成方应从 `architecture.json` 读取当前资源，不硬编码十个模块、六条路径或统一的输出等级。新增路径必须说明能形成什么成果、需要哪些材料、关键失败会如何改变结论，以及怎样继续；新增格式必须有其具体任务理由。
